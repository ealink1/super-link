# 第二轮内存精简设计

用户要求在第一轮修复后的约 279.3 MB 主进程占用基础上继续精简；保留完整中文、
Retina 清晰度、现有查询 / 表格行为和一比一复刻目标。先测量再选择修复，
不预设最终内存上限。JVM 仍明确排除。

## 备选与取舍

1. **优先压缩 CFF 的重复指令，再延后不需要的备用字体解析。** 字符映射、
   字形、字宽和展开后的绘制轮廓必须保持一致。压缩只发生在构建阶段，
   用户无需安装 Python 工具；运行时依然使用现有 Fyne / go-text。
2. **根据负载测量约束或释放不可见页面缓存。** 检查关闭标签是否残留引用、
   主题 / 文字缓存是否重复分配。需要保留草稿、结果、编辑状态和重新打开行为，
   避免为少量节省引入频繁重排或重新解析；只落地有证据的改动。
3. **提高 GC 频率或降低图形分辨率。** 前者增加 CPU，后者影响清晰度；
   本轮不作为首选，也不在产品加入周期强制 GC。图形缓冲计入进程 footprint，
   不能把整个占用都当作 Go 堆，也不能承诺完整 Retina 窗口低于 100 MB。

## 实施边界

- 保持应用 / 领域 / UI 分层，不新增数据库写入，不触碰 SuperLink 源码。
- 用新的私有工作区测相同窗口下的欢迎与两个查询草稿，数据为本地只读 fixture。
- 保存压缩前字体及构建，逐字核对全部字符映射、字形顺序、度量和轮廓；
  字体压缩产物只有通过兼容性检查后才进入生产资源。
- 对必要的 Fyne 修改维护固定版本、可审阅补丁、来源 / 哈希和并发测试。
- 保留原生输入、语法高亮、字体回退、主题及关闭生命周期；新增回归只覆盖实际风险。
- 修改后测同场景 GC 前的进程 footprint，单次诊断 GC 仅用于分辨存活对象，
  不能作为产品优化效果；检查 CPU / 渲染与并发回归。
- 重建应用，正常重启实际 QA并保留工作区，确认新进程和关键页面。按用户要求
  不使用浏览器，不提交、不推送。结果及剩余图形开销写入内存报告。
